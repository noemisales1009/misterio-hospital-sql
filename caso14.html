Caso 14: o banco que se corrigia sozinho

FRAUDE

19 de setembro de 2026 · Faturamento particular

Na manhã de 19 de setembro de 2026, as faturistas abriram o sistema e estranharam: contas de pacientes particulares que na véspera não tinham desconto nenhum amanheceram com 40% de desconto. A política do hospital é clara: desconto só com autorização da supervisora, e no máximo 10%. Ninguém admitiu ter mexido. Nas semanas seguintes aconteceu de novo, sempre nas mesmas contas, e o fechamento de setembro terminou com dezenas de milhares de reais a menos.

A primeira suspeita caiu na rotina noturna das 02:00, a conta de serviço que lança as diárias e recalcula as contas abertas. Só que a rotina não foi alterada há meses. A DBA do hospital lembrou de um detalhe: o banco guarda um log de alterações de estrutura (quem criou cada tabela, função ou gatilho, quando e de qual máquina) e existe uma auditoria que grava o valor antes e depois de cada mudança nas contas.

Desta vez você não vai só ler o banco: vai aprender a escrever nele, testar sem estragar nada e, no fim, consertar o estrago. A resposta deste caso é o nome completo de quem escondeu a regra dentro do banco.

Até aqui o jogo só usou SELECT, que lê sem mudar nada. Este caso ensina a alterar dados com segurança: INSERT, UPDATE … WHERE, DELETE … WHERE, RETURNING e as transações BEGIN / ROLLBACK / COMMIT, que deixam testar e desfazer. Depois você vai conhecer os gatilhos (triggers): funções que o próprio banco roda sozinho a cada mudança. Um gatilho bem feito é ótimo para auditoria; um gatilho escondido pode desviar dinheiro sem ninguém perceber. Nível avançado: dá para jogar depois do Caso 10. Travou? Abra a dica, depois a solução.

1

Escrevendo no banco sem estragar nada

INSERT · UPDATE … WHERE · DELETE … WHERE · RETURNING · BEGIN/ROLLBACK
Situação

Antes de investigar, você precisa aprender a mexer no banco, porque no fim do caso alguém vai ter que consertar as contas erradas. Mexer no banco do faturamento é como mexer no caixa de uma loja: um comando errado muda centenas de contas de uma vez. Então a regra desta fase é simples: todo teste fica dentro de uma transação, e a transação termina com ROLLBACK, que desfaz tudo.

ComandoO que fazNo dia a dia
INSERT INTO t (…) VALUES (…)cria uma linha nova“abrir uma conta nova”
UPDATE t SET … WHERE …muda colunas das linhas que cumprem o WHERE“lançar um item na conta 344”
DELETE FROM t WHERE …apaga as linhas que cumprem o WHERE“apagar a conta de teste”
RETURNING …mostra como as linhas ficaram depois do comando“conferir na hora o que mudou”
BEGIN; … ROLLBACK;abre uma transação e desfaz tudo no final“testar sem estragar”
BEGIN; … COMMIT;abre uma transação e grava tudo no final“agora é para valer”
Ferramenta nova · os três comandos que escrevem

INSERT INTO tabela (coluna1, coluna2) VALUES (valor1, valor2) cria uma linha: você diz em quais colunas e, na mesma ordem, os valores. UPDATE tabela SET coluna = novo_valor WHERE condição muda as linhas que cumprem a condição: dá para usar o valor antigo na conta, como SET valor_bruto = valor_bruto + 100. DELETE FROM tabela WHERE condição apaga as linhas que cumprem a condição.

O WHERE do UPDATE e do DELETE funciona igualzinho ao do SELECT. E aqui mora o maior perigo do SQL: sem WHERE, o comando vale para a tabela inteira. UPDATE ctp_conta SET status = 'paga' marca como paga todas as contas do hospital, e DELETE FROM ctp_conta apaga todas. O banco não pergunta “tem certeza?”.

RETURNING, no fim de um INSERT, UPDATE ou DELETE, devolve as linhas afetadas como se fosse um SELECT: RETURNING * mostra todas as colunas, RETURNING id, valor_final só essas.

Ferramenta nova · transação: o botão de desfazer

BEGIN; abre uma transação: tudo que vier depois fica “provisório”. No final, ROLLBACK; desfaz tudo como se nada tivesse acontecido, e COMMIT; grava de vez. Enquanto a transação está aberta, você já enxerga as mudanças (dá para conferir com SELECT ou RETURNING), mas nada fica gravado até o COMMIT. É assim que um profissional testa um comando perigoso: roda dentro de BEGIN, confere, e só troca ROLLBACK por COMMIT quando tem certeza.

Se der erro no meio de uma transação, o banco passa a recusar tudo com a mensagem current transaction is aborted. É só rodar ROLLBACK; sozinho para sair dela.

Faça no computador (não é missão)

Rode cada bloco abaixo inteiro, de uma vez. Todos terminam em ROLLBACK, então o banco volta ao normal no final. O resultado que aparece é o do último comando que devolve linhas (o RETURNING ou o SELECT).

-- 1) INSERT: abrir uma conta de teste e ver como ela ficou
BEGIN;
INSERT INTO ctp_conta (id, paciente_id, aberta_em, tipo, descricao, valor_bruto, desconto, valor_final, status)
VALUES (9001, 5, '2026-10-15 10:00:00', 'consulta', 'Consulta de teste', 300.00, 0, 300.00, 'aberta')
RETURNING *;
ROLLBACK;
-- 2) UPDATE com WHERE: lançar R$ 100 na conta 344 (e só nela)
BEGIN;
UPDATE ctp_conta
SET valor_bruto = valor_bruto + 100
WHERE id = 344
RETURNING id, valor_bruto, desconto, valor_final;
ROLLBACK;
-- 3) DELETE com WHERE: criar a conta de teste e apagar só ela
BEGIN;
INSERT INTO ctp_conta (id, paciente_id, aberta_em, tipo, descricao, valor_bruto, desconto, valor_final, status)
VALUES (9001, 5, '2026-10-15 10:00:00', 'consulta', 'Consulta de teste', 300.00, 0, 300.00, 'aberta');
DELETE FROM ctp_conta
WHERE id = 9001
RETURNING id, descricao;
ROLLBACK;
-- 4) O PERIGO: UPDATE sem WHERE muda a tabela inteira
BEGIN;
UPDATE ctp_conta SET status = 'paga';   -- esqueceu o WHERE!
SELECT status, COUNT(*) AS contas FROM ctp_conta GROUP BY status;
ROLLBACK;   -- ufa: desfaz tudo
Agora repare nisto

No bloco 2, você somou R$ 100 ao bruto da conta 344 e o desconto continuou 0.00, como esperado. Faça exatamente a mesma coisa com a conta 346 e compare o desconto antes e depois:

-- 5) O mistério: o mesmo UPDATE, agora na conta 346
SELECT id, valor_bruto, desconto, valor_final FROM ctp_conta WHERE id = 346;
BEGIN;
UPDATE ctp_conta
SET valor_bruto = valor_bruto + 100
WHERE id = 346
RETURNING id, valor_bruto, desconto, valor_final;

O que você deve ter visto

A conta 346 tinha bruto de 6.854,00 e desconto de 2.741,60. Você só mandou somar 100 no bruto, mas o RETURNING mostra o desconto em 2.781,60: ele subiu R$ 40 sozinho, exatamente 40% dos 100 que você lançou. Você não escreveu nada sobre desconto. Alguma coisa dentro do banco escreveu. Guarde isso: as próximas fases explicam.

Atenção

Se você rodar um INSERT, UPDATE ou DELETE sem ROLLBACK no final (ou com COMMIT), a mudança fica gravada no banco deste computador, e os números das missões podem sair diferentes dos que aparecem em “Para conferir”. Clique em Reiniciar banco para voltar tudo ao ponto de partida. No Supabase, rode o caso14.sql de novo.

Sua missão
  • A política diz que desconto passa no máximo de 10% do bruto. Quantas contas têm desconto acima de 10% do valor_bruto, de quantos pacientes diferentes, e quanto dá a soma desses descontos?
  • Agora quebre essas mesmas contas por paciente_id: quantas contas e quanto de desconto cada paciente teve. Ordene pelo paciente_id.
Dica

“Acima de 10% do bruto” vira WHERE desconto > valor_bruto * 0.10. Na primeira, use COUNT(*), COUNT(DISTINCT paciente_id) e SUM(desconto). Na segunda, a mesma condição com GROUP BY paciente_id e ORDER BY paciente_id.

Ver solução
SELECT COUNT(*) AS contas,
       COUNT(DISTINCT paciente_id) AS pacientes,
       SUM(desconto) AS total_desconto
FROM ctp_conta
WHERE desconto > valor_bruto * 0.10;
SELECT paciente_id, COUNT(*) AS contas, SUM(desconto) AS desconto
FROM ctp_conta
WHERE desconto > valor_bruto * 0.10
GROUP BY paciente_id
ORDER BY paciente_id;

Para conferir: 22 contas, de apenas 7 pacientes, somando R$ 43.394,25 de desconto fora da política. Os pacientes são os de número 12, 27, 33, 48, 59, 71 e 84, cada um com 2 a 4 contas. Os descontos legítimos do hospital (5% ou 10%, autorizados pela supervisão) não entram nessa conta.

O antes e o depois: a tabela de auditoria

auditoria · OLD/NEW · COUNT(*) FILTER
Situação

Em 31 de agosto, a DBA Regina Varela implantou uma auditoria nas contas particulares (chamado CHG-2026-0311). Desde então, cada UPDATE que muda o bruto, o desconto ou o valor final de uma conta deixa uma linha em ctp_auditoria: qual conta, quando, qual login do banco fez o comando, e os valores antes e depois. É a câmera de segurança do faturamento. Se alguém mexeu no desconto, a mudança está gravada ali.

ComandoO que fazNo dia a dia
OLDa linha como estava antes do UPDATE“o desconto de ontem”
NEWa linha como vai ficar depois do UPDATE“o desconto de hoje”
current_usero login do banco que está rodando o comando“quem apertou o botão”
COUNT(*) FILTER (WHERE …)conta só as linhas que cumprem a condição“quantas mudanças passaram da política”
Ferramenta nova · o gatilho de auditoria, do jeito certo

Um gatilho (trigger) é uma função que o banco roda sozinho quando acontece alguma coisa numa tabela. Dentro dele existem duas linhas especiais: OLD, a linha como estava antes, e NEW, a linha como vai ficar depois. A auditoria do hospital é um gatilho AFTER UPDATE: ele roda depois que a mudança já aconteceu e apenas copia OLD e NEW para a tabela de auditoria, junto com current_user. Ele não altera nada na conta: só registra. O WHEN (…) faz o gatilho só disparar quando algum valor mudou de fato, para não encher a auditoria de linhas iguais. Este é o código que está no banco (só para ler):

CREATE OR REPLACE FUNCTION ctp_fn_auditoria() RETURNS trigger
LANGUAGE plpgsql AS $$
BEGIN
  INSERT INTO ctp_auditoria (conta_id, momento, usuario_db,
         valor_bruto_antes, valor_bruto_depois, desconto_antes, desconto_depois,
         valor_final_antes, valor_final_depois)
  VALUES (NEW.id, localtimestamp(0), current_user,
         OLD.valor_bruto, NEW.valor_bruto, OLD.desconto, NEW.desconto,
         OLD.valor_final, NEW.valor_final);
  RETURN NEW;
END;
$$;

CREATE TRIGGER ctp_trg_auditoria
  AFTER UPDATE ON ctp_conta
  FOR EACH ROW
  WHEN (OLD.valor_bruto IS DISTINCT FROM NEW.valor_bruto
     OR OLD.desconto IS DISTINCT FROM NEW.desconto
     OR OLD.valor_final IS DISTINCT FROM NEW.valor_final)
  EXECUTE FUNCTION ctp_fn_auditoria();

Sua missão
  • Para cada usuario_db da auditoria, mostre quantas alterações ele fez no total e quantas deixaram o desconto acima de 10% do bruto (compare desconto_depois com valor_bruto_depois). Ordene do login com mais alterações para o com menos.
  • Pegue só as alterações que deixaram o desconto acima de 10%. Calcule o percentual do desconto sobre o bruto, arredondado sem casas (round(100 * desconto_depois / valor_bruto_depois)), e agrupe por esse percentual, mostrando quantas alterações e o primeiro momento em que cada percentual apareceu.
Dica

Primeira: COUNT(*) e COUNT(*) FILTER (WHERE desconto_depois > valor_bruto_depois * 0.10) com GROUP BY usuario_db. Segunda: WHERE desconto_depois > valor_bruto_depois * 0.10, o round(…) no SELECT com um apelido, e GROUP BY nesse apelido, com COUNT(*) e MIN(momento).

Ver solução
SELECT usuario_db,
       COUNT(*) AS alteracoes,
       COUNT(*) FILTER (WHERE desconto_depois > valor_bruto_depois * 0.10) AS acima_da_politica
FROM ctp_auditoria
GROUP BY usuario_db
ORDER BY alteracoes DESC;
SELECT round(100 * desconto_depois / valor_bruto_depois) AS percentual,
       COUNT(*) AS alteracoes,
       MIN(momento) AS primeira_vez
FROM ctp_auditoria
WHERE desconto_depois > valor_bruto_depois * 0.10
GROUP BY percentual;

Para conferir: a primeira traz 5 logins. svc_faturamento (a rotina noturna) tem 345 alterações, 24 acima da política; as faturistas bianca.arruda (192 / 15) e edson.quintela (166 / 9) também aparecem; silvia.miranda tem 18 alterações, todas no mesmo minuto, com 1 acima; e jussara.moura, a única que autoriza descontos, tem 31 alterações e nenhuma acima de 10%. A segunda traz uma linha só: 40%, em 49 alterações, a primeira em 19/09/2026 às 02:00:05.

Repare no que isso quer dizer. Quatro logins diferentes, de dia e de madrugada, “deram” desconto de exatamente 40%, sempre o mesmo número, e nenhum deles é quem autoriza desconto. Uma pessoa digitando não acerta 40% redondo 49 vezes. A rotina noturna parece a culpada, mas a faturista que só lança itens também “aplicou” 40%. O desconto está sendo recalculado por dentro do banco, em qualquer UPDATE dessas contas, como você viu na conta 346. E isso começou na madrugada de 19 de setembro.

O gatilho escondido

CREATE TRIGGER · BEFORE/AFTER · information_schema.triggers · pg_proc
Situação

Se o desconto muda sozinho em qualquer UPDATE, o suspeito número um é um outro gatilho na tabela ctp_conta: um que não registra, e sim altera a linha antes de ela ser gravada. O banco guarda a lista de todos os gatilhos e o código de todas as funções. É só saber onde perguntar.

ComandoO que fazNo dia a dia
CREATE TRIGGER … BEFORE UPDATEroda a função antes de gravar, e ela pode mudar o NEW“corrigir a linha antes de salvar”
CREATE TRIGGER … AFTER UPDATEroda a função depois de gravar“registrar o que mudou”
information_schema.triggerslista os gatilhos de cada tabela“o que roda escondido na tabela”
pg_triggero catálogo interno de gatilhos do PostgreSQL“inclusive se está ligado”
pg_proc.prosrco código-fonte de cada função“ler o que o gatilho faz”
pg_get_functiondef(…)a função inteira, com o CREATE“guardar a prova”
Ferramenta nova · gatilho e função de gatilho

Um gatilho tem duas partes. A função de gatilho é o código, escrito em plpgsql (a linguagem de programação do PostgreSQL), e devolve o tipo especial trigger. O gatilho em si liga essa função a uma tabela e a um evento:

CREATE TRIGGER nome BEFORE INSERT OR UPDATE ON tabela FOR EACH ROW EXECUTE FUNCTION minha_funcao();

A palavra que importa é BEFORE (antes) ou AFTER (depois). Num gatilho BEFORE, a função recebe o NEW e pode mudar os valores antes de a linha ser gravada; o que ela devolver com RETURN NEW é o que vai para a tabela. Ou seja: você manda gravar uma coisa, o gatilho troca por outra, e o RETURNING mostra o valor trocado. Foi isso que aconteceu na conta 346. FOR EACH ROW quer dizer “uma vez para cada linha afetada”.

Para achar gatilhos: information_schema.triggers mostra uma linha por gatilho e por evento (um gatilho de INSERT OR UPDATE aparece duas vezes), com action_timing (BEFORE/AFTER) e action_statement (qual função ele chama). Para ler o código: pg_proc tem uma linha por função, com o nome em proname e o corpo em prosrc. pg_get_functiondef('nome_da_funcao'::regproc) devolve a função inteira, pronta para ser recriada.

Crie o seu próprio gatilho (faça no computador)

No PostgreSQL até o CREATE pode ficar dentro de uma transação. Este bloco cria uma função e um gatilho BEFORE UPDATE que passa a descrição para maiúsculas, testa numa conta e desfaz tudo, inclusive o gatilho.

BEGIN;
CREATE FUNCTION ctp_fn_demo_maiusculas() RETURNS trigger
LANGUAGE plpgsql AS $$
BEGIN
  NEW.descricao := upper(NEW.descricao);   -- muda o NEW antes de gravar
  RETURN NEW;
END;
$$;
CREATE TRIGGER ctp_trg_demo_maiusculas
  BEFORE UPDATE ON ctp_conta
  FOR EACH ROW EXECUTE FUNCTION ctp_fn_demo_maiusculas();
UPDATE ctp_conta SET descricao = 'consulta de retorno' WHERE id = 344
RETURNING id, descricao;
ROLLBACK;   -- some a função, o gatilho e a mudança
-- Os gatilhos no catálogo interno: os RI_ConstraintTrigger são do próprio banco
-- (cuidam da chave estrangeira); tgenabled = 'O' quer dizer ligado
SELECT tgname, tgrelid::regclass AS tabela, tgenabled, tgisinternal
FROM pg_trigger
WHERE tgrelid = 'ctp_conta'::regclass;
Sua missão
  • Liste os gatilhos da tabela ctp_conta em information_schema.triggers (filtre por event_object_table): mostre trigger_name, event_manipulation, action_timing e action_statement, ordenando pelo nome e pelo evento.
  • Leia o código das funções que esses gatilhos chamam: em pg_proc, mostre proname e prosrc das funções cujo nome começa com ctp_fn, em ordem de nome.
  • A função suspeita tem uma lista de números de paciente escrita dentro dela. Use essa lista para contar as contas desses pacientes com desconto maior que zero e somar esses descontos.
Dica

Primeira: WHERE event_object_table = 'ctp_conta' ORDER BY trigger_name, event_manipulation. Segunda: FROM pg_proc WHERE proname LIKE 'ctp_fn%' ORDER BY proname. Terceira: copie a lista do IF NEW.paciente_id IN (…) para um WHERE paciente_id IN (…) AND desconto > 0, com COUNT(*) e SUM(desconto).

Ver solução
SELECT trigger_name, event_manipulation, action_timing, action_statement
FROM information_schema.triggers
WHERE event_object_table = 'ctp_conta'
ORDER BY trigger_name, event_manipulation;
SELECT proname, prosrc
FROM pg_proc
WHERE proname LIKE 'ctp_fn%'
ORDER BY proname;
SELECT COUNT(*) AS contas, SUM(desconto) AS total_desconto
FROM ctp_conta
WHERE paciente_id IN (12, 27, 33, 48, 59, 71, 84)
  AND desconto > 0;

Para conferir: a primeira traz 3 linhas. ctp_trg_auditoria é AFTER UPDATE e chama ctp_fn_auditoria(), a auditoria da fase 2. O outro, ctp_trg_ajuste_centavos, aparece duas vezes (INSERT e UPDATE), sempre BEFORE, e chama ctp_fn_ajuste_centavos(). A segunda traz as 2 funções. O comentário da suspeita diz “ajuste de arredondamento de centavos”, mas o código faz outra coisa: IF NEW.paciente_id IN (12, 27, 33, 48, 59, 71, 84) THEN NEW.desconto := round(NEW.valor_bruto * 0.40, 2). Ou seja, para sete pacientes escolhidos a dedo, todo INSERT ou UPDATE sai com 40% de desconto, não importa quem rodou o comando. A terceira confirma: 22 contas e R$ 43.394,25, exatamente o que a fase 1 achou.

Por isso a rotina noturna e as faturistas são descartadas: elas só rodaram UPDATEs normais, e o gatilho reescreveu o desconto no caminho. A pergunta agora é: quem criou esse gatilho?

Quem criou: o log de estrutura

log de DDL · LEFT JOIN · EXTRACT(HOUR)
Situação

Comandos que mudam dados (INSERT, UPDATE, DELETE) aparecem na auditoria. Mas um gatilho não é dado: é estrutura. Para isso o hospital tem outro registro, ctp_ddl_log, com todo CREATE, ALTER, DROP e GRANT do banco: quem, quando, de qual máquina e com qual chamado de mudança. No hospital, nenhuma mudança de estrutura deveria acontecer sem um chamado aprovado.

ComandoO que fazNo dia a dia
DDLcomandos de estrutura: CREATE, ALTER, DROP“mexer na planta da casa”
DMLcomandos de dados: INSERT, UPDATE, DELETE“mexer nos móveis”
LEFT JOIN … ONjunta, mantendo as linhas sem par“mudança sem chamado aparece com NULL”
EXTRACT(HOUR FROM momento)pega só a hora“fora do horário comercial”
Ferramenta nova · o log de DDL

A sigla DDL (Data Definition Language) é o nome dos comandos que criam ou mudam a estrutura: tabelas, colunas, índices, funções, gatilhos. DML (Data Manipulation Language) são os que mexem nos dados. A auditoria da fase 2 vigia o DML; o log de DDL vigia a estrutura. No PostgreSQL, quem preenche um log desses é um tipo especial de gatilho, o gatilho de evento (CREATE EVENT TRIGGER … ON ddl_command_end), que dispara a cada comando de estrutura no banco inteiro, e não numa tabela só. Criar um gatilho de evento exige privilégio de superusuário, então no Supabase você não vai conseguir criar um; aqui o log já vem pronto.

A coluna chamado é a autorização de mudança. Juntando com ctp_chamado por LEFT JOIN, uma mudança sem chamado aparece com as colunas do chamado em NULL.

-- Explorando: o log inteiro, em ordem
SELECT momento, usuario_db, maquina, comando, objeto, tabela, chamado
FROM ctp_ddl_log
ORDER BY momento;
Sua missão
  • No log de DDL, encontre a criação das duas funções e dos dois gatilhos da fase 3 (ctp_fn_auditoria, ctp_trg_auditoria, ctp_fn_ajuste_centavos, ctp_trg_ajuste_centavos). Mostre momento, usuario_db, comando, objeto, maquina e chamado, em ordem de momento.
  • Liste todas as mudanças de estrutura feitas fora do horário comercial (antes das 7h ou a partir das 19h), com a descrição e o aprovador do chamado (use LEFT JOIN com ctp_chamado). Mostre momento, login, máquina, objeto, chamado, descrição e aprovador, em ordem de momento.
  • O login usado no gatilho suspeito é de uma pessoa só? Veja a linha dele em ctp_usuario_db (login, tipo e descrição).
Dica

Primeira: WHERE objeto IN ('ctp_fn_auditoria', 'ctp_trg_auditoria', 'ctp_fn_ajuste_centavos', 'ctp_trg_ajuste_centavos'). Segunda: FROM ctp_ddl_log d LEFT JOIN ctp_chamado c ON c.codigo = d.chamado WHERE EXTRACT(HOUR FROM d.momento) < 7 OR EXTRACT(HOUR FROM d.momento) >= 19. Terceira: WHERE login = 'admin_sistemas'.

Ver solução
SELECT momento, usuario_db, comando, objeto, maquina, chamado
FROM ctp_ddl_log
WHERE objeto IN ('ctp_fn_auditoria', 'ctp_trg_auditoria',
                 'ctp_fn_ajuste_centavos', 'ctp_trg_ajuste_centavos')
ORDER BY momento;
SELECT d.momento, d.usuario_db, d.maquina, d.objeto, d.chamado,
       c.descricao, c.aprovado_por
FROM ctp_ddl_log d
LEFT JOIN ctp_chamado c ON c.codigo = d.chamado
WHERE EXTRACT(HOUR FROM d.momento) < 7
   OR EXTRACT(HOUR FROM d.momento) >= 19
ORDER BY d.momento;
SELECT login, tipo, descricao
FROM ctp_usuario_db
WHERE login = 'admin_sistemas';

Já ctp_fn_ajuste_centavos e ctp_trg_ajuste_centavos foram criados em 18/09/2026 às 23:41:12 e 23:43:05, pelo login admin_sistemas, da máquina NB-TERC-14, sem chamado. 5

Desligando o gatilho e achando quem estava na máquina

DROP TRIGGER · UPDATE em transação · COMMIT
Situação

Você já sabe o que aconteceu, quando e de onde. Falta consertar o banco e descobrir quem estava sentado na NB-TERC-14 naquela noite. O conserto tem uma armadilha: enquanto o gatilho estiver ligado, qualquer correção que você fizer nessas contas vai ser desfeita por ele no mesmo instante.

ComandoO que fazNo dia a dia
DROP TRIGGER nome ON tabelaapaga o gatilho“desligar a regra escondida”
DROP FUNCTION nome()apaga a função“jogar fora o código”
ALTER TABLE t DISABLE TRIGGER nomedesliga o gatilho sem apagar“suspender e guardar a prova”
UPDATE … WHERE … RETURNINGcorrige só as linhas certas e mostra o resultado“zerar os descontos indevidos”
COMMITgrava a transação de vez“agora é para valer”
Ferramenta nova · desligar primeiro, corrigir depois

DROP TRIGGER ctp_trg_ajuste_centavos ON ctp_conta; apaga o gatilho (repare que o nome da tabela vem junto, porque cada tabela pode ter um gatilho com o mesmo nome). Depois disso, DROP FUNCTION ctp_fn_ajuste_centavos(); apaga a função, que ficou sem uso. Se quiser apenas suspender e decidir depois, ALTER TABLE ctp_conta DISABLE TRIGGER ctp_trg_ajuste_centavos; desliga sem apagar. Antes de apagar uma prova, guarde uma cópia: SELECT pg_get_functiondef('ctp_fn_ajuste_centavos'::regproc); devolve a função inteira.

A ordem importa. Com o gatilho ligado, um UPDATE … SET desconto = 0 é reescrito para 40% de novo antes de ser gravado. Por isso o conserto vai todo numa transação: desliga o gatilho, corrige com UPDATE … WHERE bem filtrado, confere com RETURNING e só então decide entre ROLLBACK e COMMIT. E a auditoria da fase 2 vai registrar a correção também, com o seu login: é assim que deve ser.

Faça no computador · tentativa ingênua

Tente zerar o desconto da conta 346 com o gatilho ainda ligado e veja o RETURNING.

BEGIN;
UPDATE ctp_conta
SET desconto = 0, valor_final = valor_bruto
WHERE id = 346
RETURNING id, valor_bruto, desconto, valor_final;   -- o desconto voltou para 40%!
ROLLBACK;
Faça no computador · o conserto completo, testado

Agora sim: desliga o gatilho e zera os descontos acima da política só dos sete pacientes da lista. O RETURNING mostra as contas corrigidas. Termina em ROLLBACK, então nada fica gravado.

BEGIN;
DROP TRIGGER ctp_trg_ajuste_centavos ON ctp_conta;
UPDATE ctp_conta
SET desconto = 0, valor_final = valor_bruto
WHERE paciente_id IN (12, 27, 33, 48, 59, 71, 84)
  AND desconto > valor_bruto * 0.10
RETURNING id, paciente_id, status, valor_bruto, desconto, valor_final;
ROLLBACK;
Para valer de verdade

O mesmo conserto, agora com COMMIT. Ele apaga o gatilho e a função e grava as 22 correções (as contas já pagas viram cobrança da diferença). Só rode se quiser ver o banco consertado.

BEGIN;
DROP TRIGGER ctp_trg_ajuste_centavos ON ctp_conta;
DROP FUNCTION ctp_fn_ajuste_centavos();
UPDATE ctp_conta
SET desconto = 0, valor_final = valor_bruto
WHERE paciente_id IN (12, 27, 33, 48, 59, 71, 84)
  AND desconto > valor_bruto * 0.10;
COMMIT;
SELECT COUNT(*) AS contas_fora_da_politica FROM ctp_conta WHERE desconto > valor_bruto * 0.10;
Atenção

Esse último bloco muda o banco de verdade: depois dele, a fase 1 vai achar 0 contas fora da política, a fase 3 não vai mais encontrar o gatilho suspeito, e a auditoria ganha 22 linhas novas. É o resultado esperado de um conserto. Para voltar ao ponto de partida, clique em Reiniciar banco (no Supabase, rode o caso14.sql de novo).

Ver solução
