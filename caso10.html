Caso 10: a invasão

INCIDENTE

10 de outubro de 2026 · Portal do Paciente

Na madrugada de 10 de outubro de 2026, resultados de exame de dezenas de pacientes do hospital apareceram à venda na internet. A denúncia chegou pelo próprio convênio: alguém estava oferecendo laudos reais, com nome e tudo, em um fórum qualquer.

O vazamento veio do Portal do Paciente, o site onde cada pessoa consulta seus próprios exames. O time de TI isolou o servidor e trouxe uma pista: o site monta a consulta ao banco colando direto o texto que a pessoa digita na caixa de busca de exames, sem nenhum cuidado. Isso é uma porta aberta chamada injeção de SQL.

O servidor registra toda requisição que recebe: IP, horário, o texto exato do parâmetro, se deu certo e quantas linhas voltaram. É nesse log — a tabela portal_requisicao — que está a história completa do ataque, minuto a minuto. A resposta deste caso é o nome completo de quem invadiu.

Este é o segundo caso de segurança da série. A novidade é olhar para três ideias que não aparecem nas consultas do dia a dia, mas são essenciais: injeção de SQL (como um campo de busca mal escrito vira uma porta aberta), menor privilégio (dar só o acesso que cada papel precisa, nem mais) e RLS — Row Level Security, as regras que limitam quais linhas cada papel pode ver. Dá para jogar depois do Caso 9. Travou? Abra a dica, depois a solução.

Atenção: nas datas deste caso

Aqui as datas são datas de verdade (date) e as requisições são instantes com data e hora (timestamp). Escreva entre aspas simples, ano-mês-dia.

Neste casoEscreva assim
✅ CertoWHERE data = '2026-03-10'
✅ CertoWHERE momento >= '2026-03-10 02:00:00'
❌ ErradoWHERE data = 20260310, porque número não é data aqui

Nos Casos 1 a 3 a data era um número, como 20260310. Para saber qual é o caso de cada coluna, olhe o tipo no mapa das tabelas: integer é número, e date ou timestamp é data de verdade.

1

O que é injeção de SQL

LIKE · ILIKE · aspas dentro de texto
Situação

A busca de exames do portal monta a consulta assim, colando o texto digitado direto na string: "SELECT codigo, exame, data, status FROM exame_pedido WHERE codigo = '" + texto + "'". Se texto for EX-24871, tudo bem. O problema é que o banco não sabe de onde veio aquele texto: ele só vê o comando final, pronto, e executa o que estiver escrito.

ComandoO que fazNo dia a dia
LIKEcompara com um padrão usando %“busca que começa com 'Mar'”
ILIKEigual ao LIKE, ignorando maiúsculas“mar, Mar e MAR”
''duas aspas simples dentro de um texto viram uma aspa“O'Brien escreve-se 'O''Brien'”
%' OR '1'='1texto que muda o sentido da consulta quando é concatenado“o truque do invasor”
o que a pessoa digitaa consulta que o banco recebe
EX-24871… WHERE codigo = 'EX-24871' (normal)
' OR '1'='1… WHERE codigo = '' OR '1'='1' — a condição fica sempre verdadeira, devolve a tabela inteira
' UNION SELECT … --… WHERE codigo = '' UNION SELECT … --' — soma outra consulta (de outra tabela!) ao resultado
-- no finaltudo que vem depois na linha é tratado como comentário e some, mesmo que sobrasse uma aspa solta
Ferramenta nova · LIKE, ILIKE e aspas dentro de texto

LIKE padrão compara texto com curingas: % é "qualquer coisa" e _ é "um caractere qualquer". ILIKE faz o mesmo sem diferenciar maiúsculas de minúsculas — útil porque um ataque pode vir em UNION, Union ou union. Para procurar um texto que contenha uma aspa simples, escreva duas aspas simples seguidas dentro do literal: o padrão para achar ' or se escreve '%'' or %'.

padrãoo que acha
parametro ILIKE '%union%'contém union, em qualquer caixa
parametro LIKE '%--%'contém dois hifens seguidos (comentário SQL)
parametro ILIKE '%'' or %'contém uma aspa seguida de or (o '' representa UMA aspa dentro do texto)
-- Dá uma espiada nos parâmetros mais estranhos do log (não é missão, é só para explorar)
SELECT ip, parametro, status
FROM portal_requisicao
WHERE parametro LIKE '%--%'
LIMIT 15;
Sua missão
  • Quantas requisições têm, no parametro, o padrão ' or (um OR sempre verdadeiro) ou -- (corta o resto do comando) ou as palavras union e select juntas? Conte o total.
  • Agora agrupe essas mesmas requisições por ip e conte quantas cada IP tem. Vai aparecer mais de um IP suspeito — guarde os dois números, a próxima fase explica qual é qual.
Dica

Para a aspa dentro do padrão do ILIKE, escreva '' (duas aspas simples) onde você quer UMA aspa: '%'' or %'. Junte as três condições com OR, e lembre de colocar a condição de union+select entre parênteses: (parametro ILIKE '%union%' AND parametro ILIKE '%select%') OR parametro ILIKE '%'' or %' OR parametro LIKE '%--%'. Na segunda missão, é a mesma condição com GROUP BY ip.

Ver solução
SELECT COUNT(*) AS suspeitas
FROM portal_requisicao
WHERE (parametro ILIKE '%union%' AND parametro ILIKE '%select%')
   OR parametro ILIKE '%'' or %'
   OR parametro LIKE '%--%';
SELECT ip, COUNT(*) AS suspeitas
FROM portal_requisicao
WHERE (parametro ILIKE '%union%' AND parametro ILIKE '%select%')
   OR parametro ILIKE '%'' or %'
   OR parametro LIKE '%--%'
GROUP BY ip
ORDER BY suspeitas DESC;

Para conferir: 59 requisições suspeitas no total, vindas de dois IPs: 198.51.100.23 com 50 e 203.0.113.59 com 9. Qual dos dois é o ataque de verdade? É o que a próxima fase descobre.

2

A linha do tempo de cada IP

ORDER BY · MIN/MAX · COUNT(*) FILTER
Situação

Dois IPs apareceram na fase anterior com requisições suspeitas. Só que "suspeito" não é a mesma coisa que "culpado": um deles pode ser só um bot de varredura, daqueles que testam o mesmo punhado de ataques prontos em qualquer site, o dia inteiro, sem nunca ter sucesso. Para separar o bot do ataque de verdade, é preciso olhar a sequência de cada IP: quando começou, quando parou, e principalmente, o que conseguiu.

ComandoO que fazNo dia a dia
ORDER BY momentoordena pelo horário“linha do tempo do ataque”
MIN(x) / MAX(x)primeiro e último instante“início e fim do ataque”
COUNT(*) FILTER (WHERE …)conta só o que cumpre a condição“tentativas que retornaram dados”
GROUP BY ipuma linha por origem“a atividade de cada IP”
Ferramenta nova · resumindo uma sequência em uma linha

MIN(coluna) e MAX(coluna) trazem o menor e o maior valor de um grupo — com datas, o mais antigo e o mais recente. COUNT(*) FILTER (WHERE condição) conta só as linhas do grupo que cumprem a condição, sem precisar de uma consulta separada para cada contagem: dá para colocar vários COUNT(*) FILTER (…) diferentes no mesmo SELECT.

o que queremos sabercomo calcular
primeira tentativa suspeita daquele IPMIN(momento)
última tentativa suspeita daquele IPMAX(momento)
quantas vezes deu erro de sintaxe (500)COUNT(*) FILTER (WHERE status = 500)
quantas vezes funcionou e trouxe um vazamento grande (200, mais de 10 linhas)COUNT(*) FILTER (WHERE status = 200 AND linhas > 10)
Lembrete · o que cada status conta

403 quer dizer que o firewall bloqueou a requisição antes dela chegar ao banco — nunca vira um 500 nem um 200, porque nunca chega a executar nada. 500 quer dizer que chegou ao banco e o banco reclamou (geralmente sintaxe SQL errada). 200 quer dizer que o banco executou e devolveu alguma coisa — o que foi devolvido é que importa.

Sua missão
  • Para cada IP com alguma requisição suspeita (mesmo filtro da fase anterior), mostre numa linha só: o IP, a primeira e a última tentativa, quantos erros 500 e quantos sucessos (200 com mais de 10 linhas) ele teve. Ordene do IP com mais sucessos para o com menos.
Dica

Use o filtro da fase anterior no WHERE, agrupe por ip e coloque MIN(momento), MAX(momento), COUNT(*) FILTER (WHERE status = 500) e COUNT(*) FILTER (WHERE status = 200 AND linhas > 10) no SELECT. Termine com ORDER BY na contagem de sucessos, decrescente.

Ver solução
SELECT ip,
       MIN(momento) AS primeira_tentativa,
       MAX(momento) AS ultima_tentativa,
       COUNT(*) FILTER (WHERE status = 500) AS erros_500,
       COUNT(*) FILTER (WHERE status = 200 AND linhas > 10) AS sucessos
FROM portal_requisicao
WHERE (parametro ILIKE '%union%' AND parametro ILIKE '%select%')
   OR parametro ILIKE '%'' or %'
   OR parametro LIKE '%--%'
GROUP BY ip
ORDER BY sucessos DESC;

Para conferir: o IP 198.51.100.23 espalha tentativas pelos três dias, sempre bloqueadas (0 erros 500 e 0 sucessos) — é só o bot de varredura, pode descartar. Já o IP 203.0.113.59 concentra tudo numa janela curta na noite de 10/10, com 3 erros 500 (tentando acertar a sintaxe) e 3 sucessos grandes — esse é o ataque de verdade.

3

UNION SELECT: somando tabelas que não deviam aparecer juntas

UNION SELECT · information_schema
Situação

Depois de descobrir que o campo aceitava um OR sempre verdadeiro, o próximo passo clássico de quem ataca é o UNION SELECT: ele soma ao resultado as linhas de outra consulta, desde que o número de colunas seja igual. A busca de exames do portal devolve 4 colunas (codigo, exame, data, status), então um UNION SELECT também precisa vir com 4 colunas — e foi exatamente por isso que algumas tentativas do IP invasor deram erro 500: contagem de colunas errada.

ComandoO que fazNo dia a dia
UNION SELECTjunta ao resultado outra consulta com as mesmas colunas“o invasor puxa outra tabela”
information_schemacatálogo do banco: lista de tabelas e colunas“o mapa que o invasor consulta”
tabela.colunamostra de onde veio cada dado“o que vazou e de onde”
COUNT(*)quantos registros foram expostos“quantos pacientes”
Ferramenta nova · information_schema, o mapa das tabelas

information_schema.tables lista as tabelas que existem no banco, e information_schema.columns lista as colunas de cada tabela. Qualquer pessoa com acesso ao banco pode consultar essas duas visões — inclusive quem está injetando SQL por um campo de busca. É assim que um ataque "sem saber nada do banco" descobre os nomes reais das tabelas e colunas: primeiro pergunta ao banco o que existe, depois pede para ler.

-- Exatamente o que Renan usou para descobrir os nomes das tabelas e colunas
SELECT table_name FROM information_schema.tables WHERE table_schema = 'public';
SELECT column_name FROM information_schema.columns WHERE table_name = 'exame_resultado';
Sua missão
  • A partir do IP confirmado na fase anterior, liste as requisições com linhas > 0 e parametro contendo union — isso mostra a escalada, do teste mais bobo até o vazamento completo.
  • Quantos pacientes diferentes tiveram resultado de exame exposto? (Pista: a consulta vencedora do ataque devolveu a tabela exame_resultado inteira, sem filtro nenhum.)
Dica

Primeira: WHERE ip = '203.0.113.59' AND linhas > 0 AND parametro ILIKE '%union%'. Segunda: se a consulta vazou a tabela inteira sem WHERE, a resposta é simplesmente SELECT COUNT(DISTINCT paciente_login) FROM exame_resultado;

Ver solução
SELECT momento, parametro, status, linhas
FROM portal_requisicao
WHERE ip = '203.0.113.59' AND linhas > 0 AND parametro ILIKE '%union%';
SELECT COUNT(DISTINCT paciente_login) AS pacientes_expostos
FROM exame_resultado;

Para conferir: 5 requisições mostram a escalada do UNION — da tentativa trivial (1 linha) até o mapeamento das tabelas, das colunas, e por fim o vazamento completo. E 112 pacientes diferentes tiveram resultado de exame exposto: a tabela inteira de exame_resultado saiu numa única requisição.

4

Menor privilégio e RLS: duas portas que ficaram abertas

GRANT/REVOKE · ROW LEVEL SECURITY · pg_policies
Situação

A injeção de SQL foi a porta de entrada, mas duas outras decisões tornaram o estrago muito maior do que precisava ser. Primeira: o papel que o site usa para falar com o banco, portal_web, recebeu privilégio demais — mais do que uma busca de exames jamais precisaria. Segunda: as tabelas têm RLS (Row Level Security) ligado, mas a política de segurança não filtra nada de verdade.

Ferramenta nova · GRANT, REVOKE e RLS em termos simples

GRANT privilégio ON tabela TO papel dá um privilégio a um papel; REVOKE privilégio ON tabela FROM papel tira. Menor privilégio quer dizer: dê só o que aquele papel realmente usa — se o site só lê dados, não devia ter INSERT, UPDATE nem DELETE. Já o RLS é outra camada, por linha: ALTER TABLE t ENABLE ROW LEVEL SECURITY liga a trava, e CREATE POLICY nome ON t USING (condição) decide quais linhas cada papel pode ver. O problema é quando a condição é USING (true): "verdadeiro" não filtra nada, então a trava está ligada mas não tranca porta nenhuma.

comandoo que faz
GRANT SELECT ON t TO papeldeixa papel ler t
REVOKE INSERT ON t FROM papeltira de papel o direito de inserir em t
ALTER TABLE t ENABLE ROW LEVEL SECURITYliga o filtro por linha em t
CREATE POLICY nome ON t USING (condição)só mostra as linhas em que condição é verdadeira
USING (true)condição sempre verdadeira — RLS ligado, mas sem filtrar nada
Veja a falha funcionando (não é missão — é para você testar no computador)

Troque de papel para portal_web, exatamente como o site faz, e peça resultados de exame sem filtrar por paciente nenhum. Se o RLS estivesse funcionando de verdade, isso não devia devolver nada sem antes dizer de quem é a sessão.

SET ROLE portal_web;
SELECT paciente_login, exame, resultado
FROM exame_resultado
LIMIT 5;
RESET ROLE;
O que você deve ter visto

Mesmo como portal_web — o papel do site, não o dono do banco — a consulta devolveu linhas de vários pacientes diferentes, de uma vez, sem pedir login de ninguém. O RLS está ligado (você pode confirmar na missão 2), mas a política deixa passar tudo.

Sua missão
  • Veja o que o papel portal_web pode fazer em cada tabela: consulte information_schema.role_table_grants filtrando por esse papel, mostrando a tabela e o tipo de privilégio.
  • Veja as políticas de RLS das três tabelas do portal em pg_policies: mostre a tabela, o nome da política e a condição (qual). Repare que a condição é igual nas três.
Dica

Primeira: SELECT table_name, privilege_type FROM information_schema.role_table_grants WHERE grantee = 'portal_web' ORDER BY table_name;. Segunda: SELECT tablename, policyname, qual FROM pg_policies WHERE tablename IN ('portal_usuario', 'exame_pedido', 'exame_resultado') ORDER BY tablename;

Ver solução
SELECT table_name, privilege_type
FROM information_schema.role_table_grants
WHERE grantee = 'portal_web'
ORDER BY table_name;
SELECT tablename, policyname, qual
FROM pg_policies
WHERE tablename IN ('portal_usuario', 'exame_pedido', 'exame_resultado')
ORDER BY tablename;

Para conferir: a primeira missão traz 12 linhas — SELECT, INSERT, UPDATE e DELETE em cada uma das 3 tabelas. Um site que só precisa mostrar exame não devia ter INSERT, UPDATE nem DELETE em nada — isso é mais privilégio do que o necessário. A segunda traz 3 linhas, uma por tabela, e a coluna qual é true nas três: RLS ligado, mas sem filtrar ninguém.

5

Consertando as duas portas

parâmetros · CREATE POLICY · current_setting
Situação

Agora que você viu as três falhas — o campo de busca colando texto direto na consulta, o papel do site com privilégio demais, e a política de RLS que não filtra nada — é hora de ver como cada uma se corrige. As duas primeiras são mudanças que valem para o código do site e para o banco; a última você pode aplicar e testar agora mesmo, no seu computador.

ComandoO que fazNo dia a dia
parâmetro ($1)o valor viaja separado do texto da consulta“a busca entra como dado, não como comando”
CREATE POLICYcria uma regra de acesso por linha“cada usuário vê só o seu”
current_setting(…)lê uma configuração da sessão“quem é o usuário agora”
ENABLE ROW LEVEL SECURITYliga a segurança por linha na tabela“fechar a porta de verdade”
Conserto 1 · parâmetros em vez de colar texto

O conserto da injeção de SQL não é no banco, é no código do site: em vez de colar o texto digitado dentro da string da consulta, o programa envia a consulta com um espaço reservado (um parâmetro, tipo $1 ou ?, dependendo da linguagem) e manda o valor digitado separado. O banco então sabe, sem dúvida, que aquele valor é só um dado — nunca um pedaço de comando. SQL puro não tem como demonstrar isso de verdade (o parâmetro é uma proteção da camada do programa, não do banco), mas a ideia fica clara na comparação:

jeito errado (concatenar texto)jeito certo (parâmetro)
"WHERE codigo = '" + texto + "'""WHERE codigo = $1", com texto enviado à parte
o banco recebe um comando já pronto, com o texto da pessoa misturado dentroo banco recebe o comando E o valor separados — não há como o valor "virar" parte do comando
Conserto 2 · tirar o privilégio que não é usado

No banco, isso é mais simples: revogue do portal_web o que ele nunca usa. Se o site só lê, ele não precisa de INSERT, UPDATE nem DELETE.

REVOKE INSERT, UPDATE, DELETE ON portal_usuario, exame_pedido, exame_resultado FROM portal_web;
Conserto 3 · uma política de RLS que filtra de verdade

Troque a política USING (true) por uma que compare o paciente da linha com o paciente da sessão atual. Aqui usamos current_setting('app.paciente_login', true) — uma configuração que o site definiria a cada sessão, logo depois do login, com o true extra dizendo "se não tiver sido definida, devolva nulo em vez de dar erro".

DROP POLICY exame_resultado_tudo ON exame_resultado;
CREATE POLICY exame_resultado_do_paciente ON exame_resultado
  FOR SELECT TO portal_web
  USING (paciente_login = current_setting('app.paciente_login', true));
Teste o conserto

Agora simule uma sessão de um paciente real: troque para o papel portal_web, defina qual é o paciente da sessão, e peça os resultados sem filtro nenhum no WHERE. A política é que vai filtrar.

SET ROLE portal_web;
SET app.paciente_login = 'antonio.souza';
SELECT paciente_login, exame, resultado FROM exame_resultado;
RESET ROLE;
Atenção

Esses três comandos alteram o mesmo banco que todas as fases do caso usam — se depois disso a fase 4 parecer "errada" (a política não vai mais aparecer como true), é só isso: você mudou o banco de verdade. Clique em Reiniciar banco para voltar tudo ao ponto de partida.

Missão final
  • Agora que você já viu o problema todo, identifique o culpado: qual paciente tinha login confirmado (sessão de verdade, não anônima) vindo do mesmo IP que, mais tarde naquela mesma noite, disparou o ataque? Confira com SELECT verificar_caso10('Nome Completo');.
Dica

Filtre portal_requisicao por ip = '203.0.113.59' e login IS NOT NULL — essas são as buscas que ele fez logado, antes do ataque anônimo. Junte com portal_usuario pelo login para pegar o nome.

Ver solução
SELECT DISTINCT r.ip, r.login, u.nome
FROM portal_requisicao r
JOIN portal_usuario u ON u.login = r.login
WHERE r.ip = '203.0.113.59' AND r.login IS NOT NULL;

Para conferir: 1 linha — o IP 203.0.113.59 aparece com login confirmado só para um paciente, nas buscas legítimas que ele fez por volta das 20h daquela mesma noite, bem antes do ataque anônimo começar às 23h.
