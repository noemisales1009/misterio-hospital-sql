Mistério no Hospital SQL

TREINO

Oficina · O banco da enfermaria

Nos casos você investiga bancos que já vêm prontos. Aqui, sem culpado e sem pressa, você faz o contrário: desenha e constrói o seu próprio banco de dados, o de uma enfermaria, com pacientes, leitos, remédios e internações.

São três fases curtas: desenhar as tabelas e as regras (1), ligar as tabelas entre si (2) e manter o banco em ordem (3).

Faça uma fase por vez. Leia a explicação, rode o exemplo, depois tente a missão sozinha. Se nunca usou SQL, comece pelo Caso 1 e volte aqui depois.

Quando terminar, siga para o Caso 2, o prontuário adulterado.

1

Desenhar o banco antes de criar

PRIMARY KEY · NOT NULL · UNIQUE · CHECK · DEFAULT
Para que serve

Nos casos você consulta bancos que já vêm prontos. Aqui quem projeta é você: nas três fases deste treino você monta, do zero, o bancozinho de uma enfermaria (pacientes, leitos, internações e remédios). Um banco bem desenhado não deixa entrar dado errado, repetido ou sem dono. Por isso a gente pensa no papel antes de digitar o CREATE TABLE.

A regra de ouro do desenho
  1. Uma tabela para cada “coisa” do mundo real: paciente, leito, medicamento.
  2. Uma linha é um exemplar da coisa (um paciente). Uma coluna é uma característica dela (o nome).
  3. Não misture coisas diferentes na mesma tabela. O leito existe mesmo vazio e troca de paciente: por isso ele é outra tabela, e não uma coluna do paciente.

Passo 3 · Criar a tabela de pacientes
CREATE TABLE enf_paciente (
  id          bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  nome        text NOT NULL,
  cpf         text UNIQUE,
  nascimento  date NOT NULL,
  peso_kg     numeric(5,2) CHECK (peso_kg > 0),
  criado_em   timestamptz DEFAULT now()
);
  • id: o banco numera sozinho, e ninguém repete.
  • nome e nascimento são obrigatórios. cpf pode ficar em branco, mas, se vier, não pode repetir.
  • peso_kg só aceita valores maiores que zero.
  • criado_em se preenche sozinho com a hora do cadastro.

Agora cadastre três pacientes. Você não preenche id nem criado_em:

INSERT INTO enf_paciente (nome, cpf, nascimento, peso_kg) VALUES
  ('Aurora Nogueira', '111.222.333-44', '1958-03-12', 68.5),
  ('Bento Carvalho',  '222.333.444-55', '1971-11-02', 82.0),
  ('Cecília Duarte',  '333.444.555-66', '1990-07-25', 59.3);
Passo 4 · Deixe o banco recusar

A graça das regras é que elas funcionam sozinhas. Rode as três tentativas abaixo, uma de cada vez. Vão dar erro, e isso é bom: o banco protegeu você de dado ruim.

-- ERRO de propósito: falta o nome (NOT NULL)
INSERT INTO enf_paciente (cpf, nascimento)
VALUES ('000.000.000-00', '2000-01-01');
-- ERRO de propósito: esse CPF já existe (UNIQUE)
INSERT INTO enf_paciente (nome, cpf, nascimento)
VALUES ('Cópia da Aurora', '111.222.333-44', '2000-01-01');
-- ERRO de propósito: peso negativo (CHECK)
INSERT INTO enf_paciente (nome, nascimento, peso_kg)
VALUES ('Teste', '2000-01-01', -5);
Bom saber

No Supabase, tabelas novas do schema public ficam acessíveis pela API pública do projeto. Aqui os dados são inventados, então tudo bem. Num banco de verdade, você protege cada tabela com o RLS (o Caso 10 ensina).

Sua missão
  • Rode o CREATE TABLE enf_paciente e os 3 pacientes do passo 3.
  • Crie, por conta própria, a tabela enf_leito com: codigo (texto, chave primária), setor (texto, obrigatório) e ativo (verdadeiro/falso, obrigatório e verdadeiro por padrão).
  • Cadastre 3 leitos, sem preencher ativo: UTI-01 (UTI), UTI-02 (UTI) e ENF-101 (Enfermaria).
  • Prove a regra: tente cadastrar outro leito com o código UTI-01. O banco precisa recusar.
  • Aperte Conferir meu banco, logo abaixo do computador.
Dica

Copie o CREATE TABLE do paciente e adapte. Chave primária de texto: codigo text PRIMARY KEY. Obrigatório com valor padrão: ativo boolean NOT NULL DEFAULT true. Para cadastrar vários de uma vez, separe as linhas do VALUES por vírgula.

Ver solução
CREATE TABLE enf_leito (
  codigo  text PRIMARY KEY,
  setor   text NOT NULL,
  ativo   boolean NOT NULL DEFAULT true
);
INSERT INTO enf_leito (codigo, setor) VALUES
  ('UTI-01',  'UTI'),
  ('UTI-02',  'UTI'),
  ('ENF-101', 'Enfermaria');

Para provar a regra, rode INSERT INTO enf_leito (codigo, setor) VALUES ('UTI-01', 'UTI');: deve aparecer um erro de chave duplicada.

2

Ligar as tabelas

FOREIGN KEY · REFERENCES · ON DELETE · tabela de ligação
Para que serve

No arquivo de papel, escrever o nome do paciente em toda internação dá erro de digitação: “Aurora N.”, “Aurora Nogueira”, “Aurora Nogeira”. No banco, cada tabela guarda uma coisa e aponta para as outras pelo número. Esse número que aponta para outra tabela é a chave estrangeira (FOREIGN KEY), e o banco confere: se o número não existe lá, ele recusa.

Passo 1 · Um paciente, várias internações

Um paciente pode ter várias internações, mas cada internação é de um só paciente (um para muitos). A internação guarda o id do paciente e o codigo do leito:

CREATE TABLE enf_internacao (
  id           bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  paciente_id  bigint NOT NULL REFERENCES enf_paciente (id),
  leito        text   NOT NULL REFERENCES enf_leito (codigo),
  entrada      timestamptz NOT NULL DEFAULT now(),
  saida        timestamptz,
  CHECK (saida IS NULL OR saida >= entrada)
);

Repare no CHECK do final: ele compara duas colunas e não deixa a saída vir antes da entrada. Agora internar os três pacientes (o INSERT … SELECT acha o id pelo nome, sem você decorar números):

INSERT INTO enf_internacao (paciente_id, leito, entrada)
SELECT id, 'UTI-01', '2026-10-10 08:00'
FROM enf_paciente WHERE nome = 'Aurora Nogueira';

INSERT INTO enf_internacao (paciente_id, leito, entrada, saida)
SELECT id, 'UTI-02', '2026-10-08 14:30', '2026-10-12 09:00'
FROM enf_paciente WHERE nome = 'Bento Carvalho';

INSERT INTO enf_internacao (paciente_id, leito, entrada)
SELECT id, 'ENF-101', '2026-10-14 19:10'
FROM enf_paciente WHERE nome = 'Cecília Duarte';
Passo 2 · O banco confere as ligações
-- ERRO de propósito: o paciente 9999 não existe
INSERT INTO enf_internacao (paciente_id, leito)
VALUES (9999, 'UTI-01');
-- ERRO de propósito: o leito UTI-99 não existe
INSERT INTO enf_internacao (paciente_id, leito)
SELECT id, 'UTI-99' FROM enf_paciente LIMIT 1;
-- ERRO de propósito: a Aurora ainda tem internação
DELETE FROM enf_paciente WHERE nome = 'Aurora Nogueira';

O último erro é o ON DELETE trabalhando: por padrão, o banco recusa apagar quem ainda é citado por outra tabela.

Passo 4 · Muitos para muitos: a tabela de ligação

Um paciente toma vários remédios, e um remédio é dado a vários pacientes. Nenhuma das duas tabelas guarda isso sozinha. A saída é uma terceira tabela, só com as duas chaves estrangeiras. A chave primária dela é o par, e assim o mesmo par não entra duas vezes:

-- o molde (troque a e b pelas suas tabelas)
CREATE TABLE a_b (
  a_id  bigint NOT NULL REFERENCES a (id),
  b_id  bigint NOT NULL REFERENCES b (id),
  PRIMARY KEY (a_id, b_id)
);
Sua missão
  • Rode o CREATE TABLE enf_internacao e as 3 internações do passo 1.
  • Crie enf_medicamento: id gerado pelo banco (chave primária), nome (texto, obrigatório e único) e unidade (texto, obrigatório).
  • Crie a tabela de ligação enf_prescricao: paciente_id (aponta para enf_paciente, com ON DELETE CASCADE), medicamento_id (aponta para enf_medicamento) e dose (numeric(7,2), obrigatória, maior que zero). A chave primária é o par paciente_id, medicamento_id.
  • Cadastre 2 medicamentos (por exemplo, Dipirona em mg e Heparina em UI) e prescreva pelo menos 2 (paciente, medicamento).
  • Liste quem ainda está internado (sem data de saída), com o setor do leito e o remédio prescrito. Quem não tem prescrição também precisa aparecer.
  • Aperte Conferir meu banco.
Dica

Na consulta final, parta de enf_internacao com WHERE saida IS NULL, ligue paciente e leito com JOIN e use LEFT JOIN para a prescrição e o medicamento: assim quem não tem remédio não some (você viu isso no Caso 1, fase D).

Ver solução
CREATE TABLE enf_medicamento (
  id       bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  nome     text NOT NULL UNIQUE,
  unidade  text NOT NULL
);

CREATE TABLE enf_prescricao (
  paciente_id     bigint NOT NULL REFERENCES enf_paciente (id) ON DELETE CASCADE,
  medicamento_id  bigint NOT NULL REFERENCES enf_medicamento (id),
  dose            numeric(7,2) NOT NULL CHECK (dose > 0),
  PRIMARY KEY (paciente_id, medicamento_id)
);
INSERT INTO enf_medicamento (nome, unidade) VALUES
  ('Dipirona', 'mg'),
  ('Heparina', 'UI');

INSERT INTO enf_prescricao (paciente_id, medicamento_id, dose)
SELECT p.id, m.id, 500
FROM enf_paciente p, enf_medicamento m
WHERE p.nome = 'Aurora Nogueira' AND m.nome = 'Dipirona';

INSERT INTO enf_prescricao (paciente_id, medicamento_id, dose)
SELECT p.id, m.id, 5000
FROM enf_paciente p, enf_medicamento m
WHERE p.nome = 'Cecília Duarte' AND m.nome = 'Heparina';
SELECT p.nome, i.leito, l.setor, m.nome AS medicamento, r.dose
FROM enf_internacao i
JOIN enf_paciente p ON p.id = i.paciente_id
JOIN enf_leito l ON l.codigo = i.leito
LEFT JOIN enf_prescricao r ON r.paciente_id = p.id
LEFT JOIN enf_medicamento m ON m.id = r.medicamento_id
WHERE i.saida IS NULL
ORDER BY p.nome;

Para conferir, com as prescrições acima: 2 pacientes internados. A Aurora está no UTI-01 com Dipirona 500, e a Cecília no ENF-101 com Heparina 5000.

3

Manter a casa em ordem

ALTER TABLE · CREATE INDEX · CREATE VIEW · DROP TABLE
Para que serve

Banco de verdade muda o tempo todo: faltou uma coluna, a busca ficou lenta, todo dia alguém repete a mesma consulta, sobrou uma tabela de teste. Esta fase é a manutenção da casa: ALTER TABLE muda a estrutura sem perder os dados, o índice acelera a busca, a view guarda uma consulta com nome, e o DROP apaga o que não serve mais.

ComandoO que fazNo hospital
ALTER TABLE … ADD COLUMNacrescenta uma colunaincluir o telefone na ficha
ALTER TABLE … RENAME COLUMNtroca o nome de uma coluna“apelido” vira “nome social”
ALTER TABLE … DROP COLUMNapaga uma coluna e o que havia nelatirar um campo que ninguém usa
CREATE INDEXcria um “índice remissivo” para a busca ficar rápidaachar o paciente pelo nome sem folhear tudo
CREATE VIEWguarda uma consulta com um nome, para usar como tabelao relatório “quem está internado agora”
DROP TABLEapaga a tabela inteirajogar fora a ficha de teste
Passo 1 · Mudar a estrutura com ALTER TABLE

Vamos treinar numa tabela de rascunho, para não mexer nas suas tabelas de verdade. Rode o bloco inteiro:

CREATE TABLE enf_rascunho (id integer, apelido text);
ALTER TABLE enf_rascunho ADD COLUMN setor text;
ALTER TABLE enf_rascunho RENAME COLUMN apelido TO nome_social;
ALTER TABLE enf_rascunho DROP COLUMN setor;

SELECT column_name, data_type
FROM information_schema.columns
WHERE table_name = 'enf_rascunho'
ORDER BY ordinal_position;

Também dá para acrescentar uma regra a uma tabela que já existe. Os dados que já estão lá precisam obedecer a ela:

ALTER TABLE enf_leito
  ADD CONSTRAINT enf_leito_codigo_maiusculo CHECK (codigo = upper(codigo));
-- ERRO de propósito: código em minúsculas agora é recusado
INSERT INTO enf_leito (codigo, setor) VALUES ('uti-09', 'UTI');
Passo 2 · Não repita dados

Uma tabela só com tudo misturado parece mais fácil, mas repete a mesma informação em muitas linhas:

Tudo numa tabela só (evite)
pacientecpftelefoneleito
Aurora Nogueira111.222.333-44(11) 90000-0001UTI-01
Aurora Nogueira111.222.333-44(11) 90000-0001ENF-101

Se o telefone da Aurora mudar, você precisa corrigir em todas as linhas, e basta esquecer uma para o banco se contradizer. Separando em enf_paciente e enf_internacao, cada dado mora em um só lugar: corrige uma vez, e todas as consultas já enxergam o valor novo. Foi isso que você fez nas fases 1 e 2.

Passo 3 · Índice: o índice remissivo do banco

Sem índice, para achar um nome o banco lê a tabela inteira. Com índice, vai direto ao ponto, como no fim de um livro. Em tabelas grandes isso faz muita diferença. O custo é um pouco de espaço e uma gravação levemente mais lenta. A chave primária e o UNIQUE já criam índice sozinhos.

CREATE INDEX idx_enf_paciente_nome ON enf_paciente (nome);

SELECT indexname, indexdef
FROM pg_indexes
WHERE tablename = 'enf_paciente';
Passo 4 · View: uma consulta com nome

Uma VIEW não guarda dados: guarda a consulta. Cada vez que você pergunta, ela roda de novo com os dados de agora.

CREATE VIEW enf_leitos_livres AS
SELECT l.codigo, l.setor
FROM enf_leito l
WHERE l.ativo
  AND NOT EXISTS (
    SELECT 1 FROM enf_internacao i
    WHERE i.leito = l.codigo AND i.saida IS NULL
  );

SELECT * FROM enf_leitos_livres;
Passo 5 · Apagar com cuidado
DROP TABLE enf_rascunho;

DROP não pergunta “tem certeza?” e não tem desfazer. O banco ainda ajuda: ele não deixa apagar uma tabela de que outras dependem.

-- ERRO de propósito: outras tabelas dependem da enf_paciente
DROP TABLE enf_paciente;
Sua missão
  • Acrescente a enf_paciente a coluna telefone (texto) e preencha o telefone de um paciente.
  • Crie um índice chamado idx_enf_internacao_paciente na coluna paciente_id da tabela enf_internacao (é por ela que o JOIN procura).
  • Crie a view enf_internados com nome, leito, setor e entrada de quem ainda está internado, e consulte com SELECT * FROM enf_internados.
  • Aperte Conferir meu banco.
Dica

A view é o SELECT da fase 2 (internação + paciente + leito, com saida IS NULL), só que escrito depois de CREATE VIEW enf_internados AS. O índice é CREATE INDEX nome ON tabela (coluna).

Ver solução
ALTER TABLE enf_paciente ADD COLUMN telefone text;

UPDATE enf_paciente
SET telefone = '(11) 90000-0001'
WHERE nome = 'Aurora Nogueira';
CREATE INDEX idx_enf_internacao_paciente ON enf_internacao (paciente_id);
CREATE VIEW enf_internados AS
SELECT p.nome, i.leito, l.setor, i.entrada
FROM enf_internacao i
JOIN enf_paciente p ON p.id = i.paciente_id
JOIN enf_leito l ON l.codigo = i.leito
WHERE i.saida IS NULL;

SELECT * FROM enf_internados;

Para conferir: a view mostra 2 pacientes (Aurora no UTI-01 e Cecília no ENF-101). O Bento já teve alta.
